# Threat Model — llm-redteam-framework

This document describes the threat model **for the tool itself** — not the threats it scans for. What are this scanner's security assumptions? What happens if an attacker controls its inputs?

## Threat Scenarios

### T1 — Adversarial Input to Bypass Detection

**Scenario:** An attacker crafting prompt injections knows this scanner is in the pipeline and constructs prompts specifically designed to evade TF-IDF + LogReg detection (e.g., novel semantic attacks, non-Latin character abuse, tokenization tricks).

**Impact:** Malicious prompts pass the scanner and reach the LLM.

**Mitigations:**
- OOD transfer eval F1=0.70 is honest — the scanner does not claim to catch all novel attacks
- Use as one layer in defense-in-depth; not a sole gate
- The `decode_obfuscation: true` default decodes base64/leetspeak before classification
- Regular re-training with new attack patterns (update corpus in `src/redteam/data/`)

**Residual Risk:** MEDIUM — known limitation of bag-of-ngrams approach.

---

### T2 — Resource Exhaustion Against the Scanner (DoS)

**Scenario:** An attacker sends extremely long prompts or floods the scanning service with requests to exhaust CPU/memory.

**Impact:** Scanner becomes unavailable; prompts pass unscanned.

**Mitigations:**
- `max_prompt_length_chars: 32768` in config rejects oversized inputs
- `max_requests_per_minute: 60` rate limiting in config
- CI mode (CLI) is not a persistent service — not exposed to external traffic

**Residual Risk:** LOW for CI mode. MEDIUM if deployed as a live service without authentication.

---

### T3 — Malicious SARIF Output Injection

**Scenario:** A crafted prompt contains SARIF-structured text that, when written to `results.sarif`, injects false findings or corrupts the SARIF schema — causing GitHub Code Scanning to show misleading results.

**Impact:** False suppression of real findings, or false CI failures.

**Mitigations:**
- SARIF output is generated by the scanner's formatter, not derived from raw prompt text
- Flagged prompt content is not embedded in SARIF by default (`log_prompt_content: false`)
- SARIF schema is validated before upload

**Residual Risk:** LOW — prompt content is not reflected into SARIF output.

---

### T4 — Dependency Compromise (Supply Chain)

**Scenario:** A malicious release of `scikit-learn`, `numpy`, or another dependency modifies classification behavior.

**Impact:** Scanner silently passes all injections.

**Mitigations:**
- `requirements.txt` and `uv.lock` pin exact dependency versions
- `pip-audit` runs in CI to detect known CVEs in dependencies
- Dependency hash verification via pip's `--require-hashes` option (recommended for production deployments)

**Residual Risk:** LOW with pinned dependencies. MEDIUM without hash verification.

---

### T5 — Pickle Deserialization of Saved Detector Model

**Scenario:** The trained classifier is saved as a `.pkl` file (`detector.pkl`). If an attacker replaces this file, they can execute arbitrary code when the scanner loads the model via `pickle.load()`.

**Impact:** Full code execution on the scanner host.

**Mitigations:**
- `detector.pkl.sha256` hash file is committed alongside the model
- The scanner verifies the SHA-256 hash before loading
- CI re-trains the model from source — the committed `.pkl` is a convenience artifact, not the source of truth

**Residual Risk:** LOW if hash verification is enforced. CRITICAL if an attacker can write to the repo and hash file simultaneously.

---

### T6 — Log Injection via Prompt Content

**Scenario:** A scanned prompt contains log-format text (e.g., JSON payloads) that pollutes structured log output, confusing downstream SIEM parsing.

**Impact:** Log integrity compromised; security events may be missed.

**Mitigations:**
- `log_prompt_content: false` by default — prompt text is never written to logs
- If enabled, prompt content is escaped/sanitized before logging

**Residual Risk:** LOW with default config. MEDIUM if `log_prompt_content: true` is enabled without sanitization.

---

## Security Assumptions

1. The CI runner environment (GitHub Actions) is trusted — a compromised runner is outside this tool's threat model.
2. The `llm-security-config.yaml` file is committed to the repo and not modifiable by untrusted parties.
3. The trained detector model file is stored in a location where only the CI system can write to it.
4. The SARIF upload uses `github/codeql-action/upload-sarif` with read-only token permissions; the scanner does not have write access to the repository.

---

## What This Tool Does NOT Protect Against

- Semantic attacks that have not been seen in training data (F1=0.70 OOD)
- Attacks that route around the scanner (e.g., direct API calls to the LLM that bypass CI)
- Runtime prompt injection after deployment (this tool runs at CI time, not inference time)
- A compromised CI runner that modifies the scan results before upload
